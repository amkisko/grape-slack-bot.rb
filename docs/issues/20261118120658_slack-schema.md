# Slack Schema implementation and audit

## Participants

Andrei Makarov (@amkisko)

## Decisions

- Keep the classic Grape HTTP resources and register Schema handlers through
  Config. Preserve the legacy response status for existing block actions.
- Use scoped callback records for view owners. Store the primary record before
  issuing a Views API request and write the view ID index after Slack supplies
  the ID. The application session supplies the user for scoped lookups.
- Run the audit from signed ingress through routing, callback storage, Slack
  requests, and HTTP egress. Use synthetic requests and WebMock responses.
  Slack renders the views and the consumer application owns worker execution.

## Effects

- 01 Session lookup. Reuse the resolved user on callback reads and writes.
- 02 Input contract. Coerce callable arguments and return HTTP 200 for Schema replies.
- 03 Signed ingress. Read the interaction and Options Load payload from the request body.
- 04 Routing. Resolve unscoped App Home actions by action ID.
- 05 View concurrency. Forward Slack's view hash on declarative updates.
- 06 Trace. Remove request values, callback IDs, and callback data from development logs.
- 07 Closure routing. Dispatch external callback IDs with a resolved session and no callback store.
- 08 Payload shape. Reject malformed object and action fields before routing.
- 09 Storage. Skip the Views API when callback storage returns false.
- 10 Allocations. Share the ingress decode with the handler. The three measured
  samples moved from 263030 to 239030 allocations per run.
- 11 Workspace boundary. Authorize the workspace from the body, reuse its ID for
  the session lookup, and acknowledge queued Schema events with an empty body.
- 12 Allocations. Reuse immutable field strings. The three measured samples
  moved from 237030 to 209030 allocations per run.
- 13 Slack fixtures. Cover the documented shortcut and submission URL paths,
  nested response URLs, and view closures with only a view ID.
- 14 Compatibility. Restore the original status for legacy block actions with
  a body and cover deletion via response URL.

Callback storage contains the application user and view routing data. The
default TTL is 15 minutes. Web API requests use the configured bot token
and response URL requests use a separate connection. The response URL reply
exposes only status. Host logging, cache retention, and Slack-side delivery
timing require the consumer environment to observe.

### Benchmark and gate

Baseline revision c50cd68. Measurement ran on Darwin arm64 with Ruby 4.0.2
and the locked dependencies. Each process warmed up with 100 operations per
stage. The fixture contains 127 JSON bytes. The load axis is operations per
stage at 250 and 1000. The Rack stage exercises the signed request from
ingress through response formatting. Parse and dispatch are separate probes.
Wall and CPU cover all three probes. CPU is the energy proxy. Peak RSS is
process lifetime, including startup and warmup. The fixture used no network
and no external storage.

- Calibration with `bundle exec ruby -Ilib benchmarks/schema.rb --self-test`
  returned p95 values of 1, 3, and 7 us for parse, Rack, and dispatch,
  respectively. The separate wall aggregate was 1 ms.
- Each sample ran `SLACK_BENCH_REPS=1000 bundle exec ruby -Ilib benchmarks/schema.rb schema`
  or substituted `legacy` for the existing handler. The lower load used
  `SLACK_BENCH_REPS=250`. The final comparison alternated the execution order.
  A Python parent read peak RSS from `resource.getrusage(resource.RUSAGE_CHILDREN)`
  after each child process. Darwin reports this value in bytes.
- The local gate uses the maximum of five samples at 1000 operations.
  Timing and RSS ceilings use the first audit round maximum plus approximately
  15 percent headroom, rounded up. The allocation ceiling tightened to 250000.
  The limits in row order are 2 us, 130 us, 4 us, 97 ms, 97 ms, 70185000 bytes,
  and 250000 allocations. Intermediate timing misses occurred in rounds
  03 (Rack p95, wall, CPU), 05 (dispatch p95), 06 (Rack p95, wall), and
  09 (Rack and dispatch p95). All five final Schema samples passed.
  The ceilings apply to this local audit.
- The five-sample Schema medians at 1000 operations were 97 us Rack p95,
  83.43 ms CPU, and 209030 allocations. The pre-audit Schema implementation
  allocated a median of 259033 objects in three samples.
- `gem build grape-slack-bot.gemspec --output "$artifact"` built both
  revisions. `wc -c` measured 26624 bytes for baseline and 34816 bytes for
  the implementation.

  Before implementation it returned 391 examples and 0 failures.

  passed. `bundle exec rbs validate` passed with the Ruby 4.1 tsort warning.

  prerequisite. `git diff -w --exit-code -- usr/lib/release_version_check.rb`
  returned zero.
